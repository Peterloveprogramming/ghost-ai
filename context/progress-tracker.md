## Open Questions

- 08-wire-editor-home.md says "the editor home page is a server component" and "pass both lists to the sidebar". The sidebar lives in `app/editor/layout.tsx` (via `EditorShell`), not `app/editor/page.tsx`, so the server fetch was placed in the layout. If a future spec wants per-project layouts or the page to own the fetch, revisit.
- 08 requires "navigate to the new workspace" and "redirect to `/editor` if deleting the active workspace" — both imply a `/editor/[projectId]` route that no spec defines. Added `app/editor/[projectId]/page.tsx` as a bare placeholder so the flows resolve; the real workspace/canvas spec should replace it (and decide whether it validates project existence / membership on load).
- 08 makes `POST /api/projects` accept a caller-supplied `id` (to keep project id == room id), which softens 07-api.md's "use the schema's existing ID strategy". The uuid default still applies when no `id` is sent. `resolveProjectId` caps length at 128 and only trims — it does not enforce a slug charset, so a client could send an arbitrary string id. Add stricter validation if untrusted clients become a concern.
- `listSharedProjects` matches `ProjectCollaborator.email` against the Clerk `currentUser()` primary email. If a user has multiple verified emails, or collaborators are keyed differently once invites exist, this query needs widening.
- 07-api.md `GET /api/projects` says "list current user's projects" and the Rules section says "use the authenticated Clerk user ID as `ownerId`". Implemented as owner-scoped only (`where: { ownerId: userId }`). architecture.md's access model also grants collaborators read access via `ProjectCollaborator.email`, but that needs a Clerk email → collaborator lookup the spec doesn't define. Revisit when the collaborator surface is built; the list query is the place to widen.
- 07-api.md doesn't specify a status for a missing `projectId` on `PATCH`/`DELETE`. Chose `404` ("Project not found") for unknown ids and `403` ("Forbidden") for a real project owned by someone else, so ownership is enforced without a blanket `403` that would hide genuine 404s. Confirm if the spec author wants `403` for both (to avoid leaking project existence).
- 07-api.md response shapes: list → `{ projects }`, create/rename → `{ project }` (create is `201`), delete → `{ success: true }`, errors → `{ error: string }`. Not dictated by the spec beyond "consistent, predictable"; lock these in when the UI consumes them.
- `proxy.ts` no longer runs `auth.protect()` on `/api/*` (handlers return their own `401`). Future API routes (Liveblocks token issuance, etc.) must therefore each enforce auth themselves — matches architecture.md invariant 3 ("enforced at every mutation boundary") but is now load-bearing.
- `--primary-foreground` and `--accent-foreground` (in the 02-theme-tokens.md mapping) have no direct ui-context.md counterpart — ui-context.md defines surface/text/accent roles but not "text on an accent-colored surface". ## Architecture Decisions

- shadcn initialized with the `base-nova` preset and `@base-ui/react` primitives (not Radix) — this was already the state of the repo before this session; kept as-is since `components.json` matched shadcn's own defaults.
- `EditorNavbar` and `ProjectSidebar` are controlled components (sidebar open/closed state, project title, and close/toggle handlers are all props) rather than managing their own state — they're described in 03-editor.md as reusable chrome that later chapters will extend, and the toggle button lives in the navbar while the `isOpen` consumer is the sidebar, so the state has to be owned by whatever future component composes both.
- Auth is enforced at the proxy (`proxy.ts`, `auth.protect()` on all non-public routes) AND `/` re-checks with `await auth()` for its own redirect. Per-route/per-mutation checks in `app/api`, Server Actions, and Liveblocks token issuance are still required (architecture.md invariant 3) — the proxy is not the only gate.
- `@clerk/nextjs` v7 pairs with `@clerk/ui` for themes (not `@clerk/themes`, which is the v6 / Core 2 package). `import { dark } from "@clerk/ui/themes"`.
- Project dialog state is shared via a `ProjectDialogsProvider` React context mounted in `EditorShell`, because the two triggers (editor-home `Plus` button, sidebar rows/footer) live in sibling subtrees (`children` vs `ProjectSidebar`) and must drive the same dialog + form + loading state. The `useProjectDialogs()` hook holds the logic; the provider runs exactly one instance and also renders the three portaled dialogs. Consumers call `useProjectDialogsContext()`.
